Yes. With those constraints, I think the application is now well-defined enough to move from an idea into a proper specification.

One useful update since our earlier discussion: **MiniMax H3/Hailuo 3.0 was released on 31 July 2026**, and it is significantly more capable than the earlier Hailuo models: it can work with text, images, video and audio references and generate clips up to 15 seconds with native audio. ([Reuters][1]) That makes it sensible to build the app around good filmmaking language rather than hard-code the UI too tightly to one generation workflow.

# CAMERA — AI Video Prompt Builder

I would name the application something along the lines of:

**CAMERA Video Prompt Builder**

with the subtitle:

**Plan one clear shot. Build one strong AI video prompt.**

The central idea is that students never have to stare at an empty prompt box and wonder what to type. They work through the six CAMERA stages, make decisions, add a small amount of their own writing, and the application assembles everything into a professionally structured prompt.

---

# 1. Technical architecture

I recommend **plain HTML + CSS + vanilla JavaScript**.

Not React, Vue, Node or anything that requires installation or a build process.

Most importantly, I would make Version 1 literally:

```text
CAMERA-Prompt-Builder/
└── index.html
```

Everything would be embedded inside that one file:

* HTML
* CSS
* JavaScript
* icons
* diagrams
* teaching material
* MiniMax prompt rules
* export system

Students:

```text
Open folder
    ↓
Double-click index.html
    ↓
Browser opens
    ↓
Start creating
```

No network.

No server.

No installation.

No account.

No external fonts.

No internet connection.

No API calls.

This is particularly useful with a `file://` application because browsers can apply awkward origin restrictions to files that try to load other local resources. A self-contained file largely sidesteps that problem. ([developer.mozilla.org][2])

---

Although it will **look like multiple pages**, I wouldn't actually load separate HTML pages.

There will be one `index.html` and JavaScript switches between screens.

That means the student's answers stay in memory as they move:

```text
   ↓
```

```text
[C] ─ [A] ─ [M] ─ [E] ─ [R] ─ [A]

```

Completed stages turn into ticks.

Students can also click a completed stage to return to it.

## Shot size

These should be **large illustrated selection cards**.

Technically they should behave like radio buttons because only one shot size should normally be selected.

For example:

```text
┌───────────────┐
│      👁        │
│ EXTREME       │
│ CLOSE-UP      │
│               │
│ Tiny details  │
│ such as eyes, │
│ hands or an   │
│ object.       │
└───────────────┘
```

Options:

| Choice            | Student explanation                                                 |
| ----------------- | ------------------------------------------------------------------- |
| Extreme close-up  | Shows a tiny detail. Good for eyes, hands or important objects.     |
| Close-up          | Shows a face clearly. Good for emotion and reactions.               |
| Medium close-up   | Head and shoulders. Good for dialogue.                              |
| Medium shot       | Usually waist up. Good for characters performing actions.           |
| Medium-long shot  | Most of the body. Good for movement while still seeing expressions. |
| Wide shot         | Shows the whole subject and surroundings.                           |
| Extreme wide shot | Shows a huge area. Good for landscapes or showing scale.            |

Each card can contain a simple **inline SVG person-and-frame diagram**.

No downloaded images are necessary.

# 5. The Guide system

This is something I think could become one of the strongest teaching parts of the application.

Every section gets:

**ⓘ Help me choose**

Clicking it opens a teaching panel.

For example:

### Close-up

**What does it look like?**

The character's face fills most of the screen.

**When should I use it?**

Use a close-up when the audience needs to notice an expression or important detail.

**Good for:**

* reactions
* emotion
* dialogue
* important objects

**Example**

> Close-up of the girl's face as her eyes widen in surprise.

**Think about**

> Do we need to see the surroundings? If yes, a medium or wide shot might work better.

That last part is particularly useful because we're teaching **decision-making**, not vocabulary memorisation.

# 6. Camera angle

Next:

### Camera angle

Again, one primary choice.

Options:

**Eye level**

> The camera is level with the subject. Feels natural and neutral.

**Low angle**

> The camera looks upwards. Can make the subject appear powerful, heroic or intimidating.

**High angle**

> The camera looks downwards. Can make the subject appear smaller or vulnerable.

**Top-down**

> The camera looks almost directly down. Useful for showing layouts, patterns or movement through an area.

**Ground level**

> Camera is very low to the ground. Makes nearby objects appear dramatic and large.

**Dutch angle**

> The horizon is tilted. Can make the scene feel strange, unstable or dangerous.

**Point of view**

> The audience sees the scene as if looking through the character's eyes.

Again, visual diagram + explanation.

# 7. Camera movement

This needs special treatment.

Students see filmmaking terminology:

### Camera movement

○ Static camera
○ Pan left
○ Pan right
○ Tilt up
○ Tilt down
○ Push in
○ Pull out
○ Track/follow subject
○ Move left
○ Move right
○ Rise upwards
○ Lower down
○ Zoom in
○ Zoom out
○ Handheld/shaking

But internally the application can convert known movements to model syntax.

For example:

```text
Track/follow subject
```

becomes internally:

```text
[Tracking shot]
```

Earlier MiniMax models officially recognised explicit commands such as `[Tracking shot]`, `[Push in]`, `[Pan left]`, `[Static shot]`, `[Tilt up]` and others; the documentation specifically notes that explicit commands improve precision. ([MiniMax API Docs][3])

I would therefore build the translation layer separately from the interface.

Something like conceptually:

```text
"tracking"
    → display: "Track/follow the subject"
    → H3 formatter: "[Tracking shot]"

"push-in"
    → display: "Move slowly towards the subject"
    → H3 formatter: "[Push in]"
```

The children never need to learn strange model syntax.

They learn filmmaking.

# 50. Saving from `index.html`

There is one browser limitation worth designing around.

A local `file://` application cannot depend reliably on the modern `showSaveFilePicker()` API because that facility is restricted to secure contexts and isn't universally supported. ([MDN Web Docs][4])

So the app should generate its file as an in-memory `Blob` and trigger an ordinary browser download, which is widely supported. ([MDN Web Docs][5])

If your school Edge/Chrome setting is:

> **Ask me what to do with each download**

students will receive the familiar Save As dialogue.

Otherwise the file goes into Downloads automatically.

We can generate sensible filenames:

```text
rainforest-explorer-shot-01.camera.json
```

and:

```text
rainforest-explorer-shot-01.md
```

---

# 51. Don't rely on browser autosave

Another consequence of running directly from `file://` is that I would **not rely on localStorage for important student work**. Browser behaviour for local file origins is not guaranteed consistently. ([MDN Web Docs][6])

We can use it opportunistically, but the app shouldn't depend on it.

Instead:

* work stays active while the page remains open;
* closing/reloading warns the student;
* JSON provides reliable Save/Open.

For example:

> ⚠ You have unsaved changes.

That could be very powerful instructionally.

# 55. H3 should be a formatter, not the application's foundation

Because H3 has literally only just been released, I wouldn't scatter H3-specific syntax throughout the code.

Instead:

```text
STUDENT CHOICE
       ↓
CAMERA internal representation
       ↓
MODEL FORMATTER
       ↓
MiniMax H3 prompt
```

Conceptually:

```javascript
modelProfiles = {
    minimaxH3: {
        tracking: "...",
        static: "...",
        pushIn: "...",
        ...
    }
}
```

Then if we discover next week that H3 prefers:

```text
camera follows subject smoothly
```

rather than:

```text
[Tracking shot]
```

we change **one mapping table**, not the entire application.

This is particularly sensible because H3 is only days old and the current public MiniMax API documentation still mainly exposes the earlier Hailuo 2.3 generation syntax. H3 itself is confirmed as the newly released model, but its local ecosystem and prompting conventions are still settling. ([Reuters][1])

# The educational model underneath it

The application would ultimately teach this sequence:

```text
I have an idea
      ↓
I make filmmaking decisions
      ↓
I describe visible actions
      ↓
I identify important details
      ↓
I check for contradictions
      ↓
The computer structures my instructions
      ↓
I review the prompt
      ↓
I generate
      ↓
I evaluate the result
      ↓
I change ONE thing
```

That's much more valuable than simply giving students a clever prompt generator.

They're learning **how to direct an AI system**.

And because the interface permanently uses:

> **C — Camera
> A — Actor
> M — Movement
> E — Environment
> R — Rendering
> A — Anchors**

after using the application repeatedly, I'd expect some of them eventually to be able to construct CAMERA prompts without the application at all.

That's the point where the scaffold has done its job.
