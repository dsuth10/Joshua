# Classroom Software Studio: Game Product Manager Project

## Unit Overview

In this project, students work in small teams to operate like a mini software studio. Their main product is a playable video game, but they must also create the supporting product materials needed to explain, advertise, test and launch it.

Students take on the role of **product managers**, **game designers**, **developers**, **artists**, **testers**, and **marketers**. They learn that a successful software product is not just a good idea. It needs planning, teamwork, testing, improvement, communication and launch materials.

---

## Recommended Year Level

**Years 5–6**

This can be simplified for Year 4 or extended for Year 7.

---

## Suggested Duration

**8–12 lessons**

Each lesson assumes approximately **45–60 minutes**.

A shorter version could run over one week as an intensive project. A deeper version could run over a full term.

---

## Core Project Challenge

> Your team is a small software studio.  
> Your job is to design, build, test, improve and launch a playable video game for a target audience.  
> You must also create the materials needed to advertise, explain and present your product.

---

## Learning Intentions

Students will learn to:

- plan and manage a digital product project
- define a target audience and user need
- design a playable video game with clear rules and goals
- break a large project into smaller tasks
- prioritise features using a simple product management system
- work collaboratively in assigned roles
- use feedback to improve a product
- create advertising and support materials for a digital product
- present and justify design decisions

---

## Success Criteria

Students are successful when they can:

- explain who their game is for and why it would appeal to that audience
- identify the smallest playable version of their game
- separate tasks into clear categories
- use a task board to track progress
- build a working game with a clear objective
- test their game with real users
- identify bugs and areas for improvement
- make changes based on feedback
- create clear product materials that explain and advertise the game
- present their product and reflect on their team process

## Team Roles

Teams of **3–5 students** work well.

Roles can be assigned for the whole project or rotated each sprint.

### Product Manager

Responsible for:

- keeping the team focused
- managing the task board
- helping the team prioritise features
- checking that the MVP is achievable
- preparing for team check-ins

The Product Manager is not the boss. Their job is to help the team make clear decisions.

### Game Designer

Responsible for:

- game rules
- difficulty
- levels
- scoring
- player experience
- win and lose conditions

### Developer

Responsible for:

- coding or building the game
- movement
- collisions
- variables
- scoring
- game logic
- debugging

### Artist / UI Designer

Responsible for:

- characters
- backgrounds
- buttons
- menus
- title screen
- visual style
- layout

### Tester / Quality Lead

Responsible for:

- testing the game
- recording bugs
- checking instructions
- organising peer feedback
- checking if the game is understandable and fun

### Marketing / Launch Lead

Responsible for:

- landing page
- poster
- pitch deck
- game trailer
- app store mock-up
- promotional writing

In smaller groups, students can combine roles.

---

## Project Structure

The project follows seven phases:

1. **Discover** — Who is the game for?
2. **Define** — What is the smallest playable version?
3. **Plan** — What tasks need to be done?
4. **Build** — Create the first playable version.
5. **Test** — Let real users try it.
6. **Improve** — Fix problems and polish the product.
7. **Launch** — Present the game and product materials.

# Lesson Sequence

## Lesson 1: Welcome to the Software Studio

### Lesson Focus

Students learn what a product manager does and understand the full project challenge.

### Teacher Preparation

Prepare:

- example game screenshots
- example app store pages or game landing pages
- team role cards
- project brief
- simple task board template

### Introduction

Explain that students are not just making a game. They are creating a **digital product**.

Discuss:

- What makes a game successful?
- Why do games need instructions?
- Why do products need advertising?
- Why do teams need a plan?
- Why is feedback useful?

### Mini Lesson: What Is a Product Manager?

A product manager helps the team answer:

- Who is this for?
- What problem or need does it solve?
- What should we build first?
- What can wait until later?
- How do we know if it is successful?

### Main Activity

Students examine a familiar game and identify:

- target audience
- game goal
- main features
- visual style
- instructions
- what makes it fun
- possible improvements

### Student Output

Each student completes a short product analysis.

```markdown
## Product Analysis

Game name:

Target audience:

Main goal:

Three key features:

What makes it fun?

What could be improved?
```

### Exit Ticket

> Why does a game team need a product manager?

## Lesson 2: Game Ideas and Target Audience

### Lesson Focus

Students form teams and develop possible game ideas.

### Teacher Preparation

Prepare:

- team list
- brainstorming template
- target audience template
- idea selection matrix

### Introduction

Explain that good product teams do not start by building immediately. They first understand the user.

### Mini Lesson: Target Audience

Students define a target audience using prompts:

- How old are they?
- What games do they enjoy?
- Do they like speed, puzzles, story, competition or creativity?
- How difficult should the game be?
- What would make them want to replay it?

### Main Activity

Teams brainstorm three possible game ideas.

Examples:

| Game Type | Possible Idea |

| Platformer | Jump across platforms and avoid hazards |
| Quiz game | Answer questions to defeat enemies |
| Survival game | Stay alive as long as possible |
| Collection game | Gather objects before time runs out |
| Puzzle game | Solve challenges to unlock the next area |
| Maths game | Use skills to earn points or build a town |

Teams score each idea from 1–5.

| Criteria | Idea 1 | Idea 2 | Idea 3 |
|---|---:|---:|---:|
| Fun |  |  |  |
| Achievable |  |  |  |

### Student Output

Each team chooses one game idea and completes:


> What is one feature your audience would care about?

## Lesson 3: MVP and Feature Prioritisation

### Lesson Focus

Students define their Minimum Viable Product and sort features by priority.

### Mini Lesson: MVP

Explain:

> The MVP is the smallest version of the game that is still playable and testable.

Use an example.

### Example

Dream version:

- 10 levels
- 5 characters
- boss battles
- shops
- upgrades
- multiplayer
- secret rooms

MVP version:

- 1 level
- 1 player
- 1 enemy
- 3 collectable items
- score
- win condition
- restart button

### Mini Lesson: MoSCoW Prioritisation

| Priority | Meaning |
|---|---|
| Must have | The game will not work without it |
| Should have | Important, but not essential |
| Could have | Nice extra |
| Won’t have yet | Too large for this version |

Teams list all possible features, then sort them.

A good primary school MVP might include:

- player movement
- one clear goal
- one obstacle or challenge
- score, timer or health
- win or lose condition
- restart option

## Lesson 4: Task Breakdown and Project Board

### Lesson Focus

Students break their project into tasks and create a Kanban board.

### Mini Lesson: Breaking Big Work into Small Tasks

Instead of writing:

> Make the game

Students write:

- create player sprite
- code player movement
- create enemy sprite
- code enemy movement
- add score variable
- add collectable object
- create title screen
- write instructions
- test collision detection

### Kanban Board

Teams use this structure:

| Backlog | Ready | Doing | Testing | Done |
|---|---|---|---|---|
| All possible tasks | Chosen for now | Being worked on | Needs checking | Fully finished |

### Task Card Template

```markdown
## Task Card

Task name:

Category:
Product / Design / Development / Art / Testing / Marketing

Priority:
Must / Should / Could

Owner:

Size:
Small / Medium / Large

Status:
Backlog / Ready / Doing / Testing / Done

Done when:
-
-
-
```

### Main Activity

Teams create at least **15–25 task cards**.

They should include tasks from different categories:

| Category | Example Tasks |
|---|---|
| Product | Define audience, write pitch, prioritise features |
| Design | Sketch level, write rules, design scoring |
| Development | Code movement, add collision, add timer |
| Art | Create sprites, background, buttons |
| Testing | Create feedback form, record bugs |
| Marketing | Design poster, landing page, pitch deck |

### Student Output

Each team has a working project board.

### Exit Ticket

> Which task must be completed first before other tasks can happen?

## Lesson 5: Paper Prototype and Game Design

### Lesson Focus

Students create a paper version of their game before building digitally.

### Mini Lesson: Prototyping

Explain:

> A prototype helps you test an idea before spending too much time building it.

A prototype can be rough. It does not need to look beautiful.

### Main Activity

Teams sketch:

- title screen
- game screen
- player
- enemies or obstacles
- collectable items
- score/timer/health display
- win screen
- lose screen

### Game Design Questions

Teams answer:

```markdown
## Game Design Plan

What does the player control?

What does the player need to do?

How does the player win?

How can the player lose?

How does the score work?

What makes the game harder?

What will the player see first?

How will the player know what to do?
```

### Peer Feedback

Pairs of teams review each other’s paper prototype.

Feedback prompts:

- I understand the goal because...
- I am confused about...
- One thing that sounds fun is...
- One suggestion is...

### Student Output

Each team updates their design based on feedback.

### Exit Ticket

> What did your team change after feedback?

---

## Lesson 6: Build Sprint 1 — Core Game

### Lesson Focus

Students build the first playable version.

### Sprint Goal

By the end of this sprint, each team should have a basic version where the player can do something meaningful.

### Recommended Build Targets

Teams should aim to complete:

- player sprite
- player movement
- basic background or level
- one collectable, obstacle or enemy
- one score, timer or health system
- simple win or lose condition

### Teacher Role

Move between teams and ask product manager questions:

- Is this part of your MVP?
- What is the most important thing to finish next?
- Is anyone blocked?
- What does “done” mean for this task?
- Can the game be tested yet?

### Student Output

A rough but playable version.

### End-of-Lesson Stand-Up

Each team answers:

```markdown
## Sprint Check-In

What did we finish today?

What are we working on next?

What problems did we find?

What needs testing?
```

---

## Lesson 7: Build Sprint 2 — Features and First Testing

### Lesson Focus

Students continue building and prepare for early testing.

### Mini Lesson: Bugs and Quality

Explain that bugs are normal. The goal is not to hide them. The goal is to find them, record them and fix the important ones.

### Bug Report Template

```markdown
## Bug Report

Bug name:

What happened?

What should have happened?

How can someone repeat the bug?

How serious is it?
Low / Medium / High

Who will fix it?

Status:
Open / Fixed / Tested
```

### Main Activity

Teams continue building their MVP.

The Tester / Quality Lead begins testing using a checklist.

### MVP Test Checklist

```markdown
## MVP Test Checklist

- [ ] The game starts correctly
- [ ] The player can move or interact
- [ ] The player understands the goal
- [ ] The scoring/timer/health works
- [ ] The player can win
- [ ] The player can lose or restart
- [ ] Instructions are clear
- [ ] No major bugs stop the game from working
```

### Student Output

Teams complete at least one round of internal testing.

### Exit Ticket

> What is the most serious bug or problem your team needs to fix?

---

## Lesson 8: User Testing and Feedback

### Lesson Focus

Students test their game with real users and collect feedback.

### Mini Lesson: Feedback Is Product Information

Explain:

> Feedback is not about whether the team is good or bad. Feedback helps the team decide what to improve.

### User Testing Rules

The game team should not explain everything. They should watch what the player does.

Students observe:

- Does the player know how to start?
- Does the player know what the goal is?
- Does the player understand the controls?
- Does the player enjoy it?
- Where does the player get stuck?
- What bugs appear?

### User Feedback Form

```markdown
## Game Testing Feedback

Game tested:

Tester name:

What did you enjoy?

What was confusing?

Was the game too easy, too hard or about right?

Did anything not work properly?

What is one improvement you suggest?

Would you play it again? Why or why not?
```

### Main Activity

Teams rotate and test each other’s games.

Each team should collect feedback from at least **3–5 testers**.

### Student Output

Teams complete a feedback summary.

```markdown
## User Testing Summary

Number of testers:

Most common positive feedback:

Most common problem:

Bugs found:

Top 3 improvements we will make:
1.
2.
3.

Feedback we will not act on yet:
-
```

### Exit Ticket

> What is one change your team will make because of user feedback?

## Lesson 9: Improve, Polish and Prepare Product Materials

### Lesson Focus

Students improve their game and begin creating launch materials.

### Mini Lesson: Polish Versus New Features

Explain the difference:

| Polish | New Feature |
|---|---|
| Improves what already exists | Adds something extra |
| Fixes confusion | Expands the game |
| Makes the MVP better | May increase workload |
| Usually safer near the deadline | Riskier near the deadline |

Examples of polish:

- clearer instructions
- better start screen
- better button labels
- smoother movement
- easier first level
- fixed bugs
- improved visual layout

### Main Activity

Teams split work:

| Student Role | Focus |
|---|---|
| Product Manager | Updates board and priorities |
| Developer | Fixes bugs |
| Designer | Improves game balance |
| Artist | Polishes visuals |
| Tester | Retests fixed bugs |
| Marketing Lead | Starts product materials |

### Required Product Materials

Each team creates:

1. **Landing page or poster**
2. **Player guide**
3. **Testing report**
4. **Pitch deck**

### Student Output

Improved game and draft launch materials.

# Assessment Rubric

## Criteria 1: Product Management and Planning

| Level | Description |
|---|---|
| A | The team clearly defined the audience, prioritised features effectively, maintained a task board and made thoughtful decisions based on time and feedback. |
| B | The team defined the audience, used a task board and made mostly sensible decisions about features and priorities. |
| C | The team had a basic plan and completed some task tracking, but priorities were not always clear. |
| D | The team had limited planning and found it difficult to manage tasks or make clear product decisions. |

## Criteria 2: Game Design

| Level | Description |
|---|---|
| A | The game has a clear goal, engaging mechanics, appropriate difficulty and a strong sense of player experience. |
| B | The game has a clear goal, mostly effective rules and some engaging features. |
| C | The game is playable but may have unclear rules, limited challenge or uneven difficulty. |
| D | The game is incomplete, confusing or difficult to play. |

## Criteria 3: Technical Creation

| Level | Description |
|---|---|
| A | The game works reliably and uses appropriate coding concepts such as events, variables, conditionals, loops or collisions effectively. |
| B | The game mostly works and includes several appropriate coding concepts. |
| C | The game has basic functionality but may contain bugs or limited coding complexity. |
| D | The game has limited functionality or significant errors that prevent play. |

## Criteria 4: Testing and Improvement

| Level | Description |
|---|---|
| A | The team gathered useful feedback, identified bugs and made clear improvements based on user testing. |
| B | The team gathered feedback and made some improvements. |
| C | The team completed basic testing but made limited improvements. |
| D | The team did little testing or did not use feedback effectively. |

## Criteria 5: Product Materials and Launch

| Level | Description |
|---|---|
| A | Product materials are clear, persuasive, visually effective and strongly connected to the game. The pitch explains decisions thoughtfully. |
| B | Product materials are clear and connected to the game. The pitch explains the product well. |
| C | Product materials are basic but mostly understandable. The pitch gives some explanation. |
| D | Product materials are incomplete, unclear or not well connected to the game. |

## Criteria 6: Collaboration and Reflection

| Level | Description |
|---|---|
| A | The student contributed consistently, communicated well, solved problems and reflected thoughtfully on the process. |
| B | The student contributed well and reflected on their role and learning. |
| C | The student made some contribution and completed a basic reflection. |
| D | The student made limited contribution or reflection was incomplete. |

# Teacher Checkpoints

Use these checkpoints to stop teams from drifting.

## Checkpoint 1: Game Concept Approval

Before building, each team must show:

- target audience
- one-sentence pitch
- game goal
- MVP feature list

Teacher question:

> Is this small enough to build and test?

## Checkpoint 2: Task Board Approval

Each team must show:

- at least 15 task cards
- clear owners
- must-have tasks identified
- no more than 1–2 tasks per student in “Doing”

Teacher question:

> Does every task have a clear “done when” condition?

## Checkpoint 3: MVP Playability

Each team must show:

- player can interact
- game has a goal
- game has a win or lose condition
- basic instructions exist

Teacher question:

> Could another student play this without your team explaining everything?

## Checkpoint 4: Feedback and Improvement

Each team must show:

- user feedback
- bug reports
- top 3 improvements
- evidence of changes

Teacher question:

> What did you change because of testing?

## Checkpoint 5: Launch Readiness

Each team must show:

- final game
- landing page or poster
- player guide
- testing report
- pitch deck

Teacher question:

> Does your launch pack help someone understand, play and want to try your game?

# Classroom Management Tips

## Keep Scope Small

Students will often want to build games that are far too large.

Use this rule:

> Build the smallest playable version first. Add extras only after it works.

## Make Work Visible

The task board is not decoration. It is evidence of project management.

Regularly ask:

- What is in Doing?
- What is blocked?
- What moved to Done?
- What needs testing?

## Separate Ideas from Commitments

Students can have a huge idea list, but only a few features should be committed to the MVP.

Use language like:

> That is a good roadmap idea, not a Version 1.0 idea.

## Test Early

Do not wait until the end to test.

A rough game tested early is more useful than a polished game tested too late.

## Reward Good Decisions

Praise teams for:

- cutting unnecessary features
- fixing bugs
- improving instructions
- using feedback
- helping another team
- finishing the MVP before adding extras

# Final Teacher Framing

The most important idea to keep returning to is:

> A successful product team does not build every idea.  
> A successful product team builds the right first version, tests it, improves it and explains it clearly.

This project gives students a real reason to practise planning, coding, design, persuasive communication, feedback, teamwork and reflection. The video game is the centrepiece, but the deeper learning comes from treating it like a real product launch.
